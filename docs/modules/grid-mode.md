# Grid mode

One switch (`shell.gridMode`, bbkOS › Grid mode since 2026-10-31; Appearance › Style before, the Shell page until 2026-10-28) that turns the desktop into flat, touching cells separated by hairline borders: no gaps between cells, no rounded corners on the shell, no shadows. Windows are the exception (2026-10-30): they keep your own corner radius (`windows.rounding`) and your own margin around them (`windows.gapsOut`), so a rounded window sits as a card inside the square bar and rail cells, as in the owner's wireframe. Since 2026-10-29 the corners of popups, buttons and controls can stay round (`shell.gridRoundControls`, "Round popups and controls in grid mode", off by default); the bar is always square; the stage previews and pinned tiles follow the windows' radius and margin (2026-10-30). The owner's own gap, radius and shadow values are not changed; they come back when the mode is switched off. Design source: the owner's own keyboard (omakey), whose keys are flat tiles with a thin dark line between them. Added 2026-10-26.

## How it works

Two layers, so nothing has to be kept in step by hand:

1. **The renderer overrides the values** (`bbkos_theme/settings.py`: `GRID_OVERRIDES`, `effective()`; used by `apply.build`). While `shell.gridMode` is on, every generated file (`colors.json`, `hypr-theme.lua`, `hyprlock.conf`, the GTK colours) is rendered from a copy of the settings with these replaced; `settings.json` itself is never touched. Because the shell reads its radii, gaps and shadow from `colors.json`, every `Theme.barRadius`, `Theme.barFloat`, `Theme.barItemGap`, `Theme.gap` and `Theme.shadowStrength` is 0 without a line of QML, and so are `Theme.radius`, `Theme.controlRadius` and `Theme.pillRadius` unless `shell.gridRoundControls` is on.

   | Setting | Value in grid mode |
   |---|---|
   | `shell.radius`, `controlRadius`, `pillRadius` | 0, unless `shell.gridRoundControls` is on (`GRID_ROUND_OFF`; the saved values then apply) |
   | `shell.barRadius` | 0 |
   | `stage.dock` | on (`Stage.qml` also reads `Theme.gridMode`, since the stage settings are not in `colors.json`) |
   | `stage.cardRadius` | the window rounding, `windows.rounding` (2026-10-30; `Theme.gridWindowRadius` in the shell) |
   | `stage.railPadding`, `stage.cardGap` | the window margin, `min(gapsOut, 32)` (`settings.grid_rail_gap`; `Theme.gridMargin` in the shell) |
   | `shell.gap`, `barFloat`, `barItemGap` | 0 |
   | `shell.barHug` | false |
   | `shell.barPills` | individual (every widget is a cell) |
   | `shell.popupShadow` | 0 |
   | `windows.gapsIn` | half the margin, `(gapsOut + 1) // 2` (`settings.grid_gaps_in`): the gap between two tiled windows equals the margin around them |
   | `windows.shadowEnabled` | false |
   | `windows.borderSize` | 1 |
   | `lock.fieldRadius` | 0 |

   Hyprland's inactive window border becomes the opaque `gridEdge` colour (below), the active border keeps the palette's accent gradient (a focus ring must stay visible).

   **One solid border colour (2026-10-30).** `colors.gridEdge` (`render.tokens`, `GRID_EDGE_STRENGTH` 0.22) is the wallpaper's `surface` colour leaned 22 % toward the text colour, as one opaque hex. Edges used to be the text colour at 22 % (shell) and 25 % (Hyprland): translucent, so they looked different over every background, and where two cells or windows overlap by a hairline the two layers stacked into a darker or lighter joint. An opaque colour paints the same everywhere and an overlap is invisible.
2. **QML handles what a token cannot say** (`Theme.gridMode`, read from `colors.json`): the cell borders (`BarItem` draws a hairline `Theme.cardEdge` around each cell and fills the bar's thickness; `BarSection` overlaps neighbours by one hairline so two cells share one line; every cell's size along the bar is rounded up to whole physical pixels and a centred group starts on a whole pixel (`Theme.wholeUp`, `Theme.whole`), so each shared line lands on one pixel row (2026-10-30: with fractional positions some joints drew two pixels wide); `Bar.qml` draws the line along the bar's inner edge, and fills every empty stretch between and around the groups with an empty cell of the same style (`body.gridFills`, from each group's `spanFrom`/`spanTo`), so the bar is one unbroken row of cells; the cells overlap their neighbours by one hairline like the widgets do), `Theme.cardEdge` itself (`Theme.gridEdge`, opaque, instead of the text colour at 8 %, so every card, popup, notification, OSD and settings card gets the stronger line), and the literal radii (toggle, slider track, halo and bead, the OSD, battery, calendar and timer progress bars, badge dots) which are 0 (`Theme.gridSquare`, grid mode without `gridRoundControls`). The stage rail's tiles and cards are not in this list since 2026-10-30: they take the windows' corner radius (`stage.cardRadius`).

**Whole physical pixels (2026-10-30, evening).** The bar's thickness is rounded up to a whole number of physical pixels while grid mode is on (`Theme.barHeight` = `wholePixels(shell.barHeight)`: the smallest length from the saved value to 15 more that is whole on the most screens; 26 → 30 at this panel's 16/15, which is 32 physical px). A layer window is a whole number of logical pixels, and at a fractional scale only some lengths are whole physical pixels (multiples of 15 at 16/15); where a fractional edge is shared by two surfaces (the bar's last row and the rail's first) the compositor redrew it from one alone and the bar's line dropped out (`dock.md`). The saved `shell.barHeight` is not changed (the Bar page still shows it) and is used as saved with the mode off. `Theme.hair` is one physical pixel from Hyprland's monitor scale (`Theme.scaleOf`); it used to read `ShellScreen.devicePixelRatio`, which is the output's integer scale (2 here), so every hairline was 0.53 physical px and was drawn or dropped by where it fell: that was the cause of the doubled joints and of the frame's "one-pixel line at y=0 is not drawn" (`quickshell.md`, Pixel-perfect rules).

## Stage rail

Since 2026-10-30 the rail also carries the pinned apps (`dock.md`), switched on by grid mode (`stage.dock` is one of its overrides, "Set by grid mode"). In grid mode the rail (`modules/stage/Stage.qml`) has the window margin (2026-10-30) as its padding and as the gap between its tiles and cards (`stage.railPadding` and `stage.cardGap`, "Set by grid mode"; with the owner's 8 px the pinned tiles sit 8 px from the rail's edges and from each other, as the windows do), the pinned tiles and the open-window cards have the windows' corner radius (`windows.rounding` through `stage.cardRadius`, "Set by grid mode"), a one-pixel `cardEdge` line runs edge to edge between the pinned section and the cards (only while there are cards), and its background is the bar's: the window colour is `Theme.barBg` (the blurred wallpaper strip, `BarBlur`, when the bar has opacity under 100 % and blur on) with `Theme.pillBg` over it, the same two layers as the bar's empty cells, and a `cardEdge` line runs along the inner edge like the bar's. `stage.railOpacity` is ignored (since 2026-10-31 in both modes: outside grid mode the rail takes the bar's style too, `dock.md`). The rail can go on any edge and hug its contents (2026-10-31, `dock.md` "Placement and style"); a hugging rail in grid mode is one cell that also draws its two ends, and its lengths are snapped to whole physical pixels like the bar's. Cards are centred vertically as before, so a short stack leaves empty rail above and below it (the bar fills its empty stretches with cells; the rail does not draw cell boundaries there).

## Windows: your margin and corner radius

`windows.gapsOut` (the margin around the windows, 8 px in the owner's settings) and `windows.rounding` are not overridden: grid mode leaves them as saved, so there is one variable for each, editable on the Windows page, and a window is a rounded card inside the bar and rail cells. The gap between two tiled windows follows the margin (2026-10-30): Hyprland puts `gaps_in` on each side of a window, so the gap between two is twice it, and `gapsIn` is half the margin (odd margins round up; the Windows page shows "Gaps inside" as "Set by grid mode"). The 1 px window border is a grid value. Backdrop: none; the margins show the wallpaper (the Zen and Arc look, where the space around the card is the chrome colour, is not built).

With a margin under 2 px the window's own border lands next to the bar's or the rail's edge line and the two draw a doubled line (measured 2026-10-30 at 0: 2 px on the top and left edges). Two ways of hiding that were tried and reverted the same day because they were fragile: Hyprland clamps a negative `gaps_out` to 0, and making the bar and rail reserve one pixel less meant the rail painted over the bar's line and needed a 1 px margin per bar position. Keep the margin at 2 px or more. (For a while the rail had a 1 px margin on the bar's side, for a different reason: the bar's last pixel row and the rail's first were the same row at a fractional scale, and a hover repaint of the rail blanked the bar's line there. Since the bar is a whole number of physical pixels thick the rail is flush again; `dock.md`.) (Until later the same day grid mode used `gapsIn` -1, so two windows shared one border line; that gave notches where the rounded corners met and is gone.)

## Border along the screen edges

A one-pixel line in `gridEdge` runs along all four edges of every screen (2026-10-30), so the desktop has one uniform border: before, only the side with the bar had one (the bar's cells draw their own edges) and the rest showed bare wallpaper or the rail's cards. `modules/frame/ScreenFrame.qml`: four thin layer windows per screen (top, bottom, left, right), empty input region, no reserved space, made only while grid mode is on.

The frame is the one owner of these lines (since the evening of 2026-10-30). It is on the Overlay layer, above the bar and the rail, so which was mapped first no longer matters; the rail no longer draws its own outer, top and bottom lines, and the bar cells' outer edges lie on the same pixel in the same opaque colour, under the frame. On the Overlay layer a fullscreen window would not cover it, so the frame removes its strips while the screen's active workspace has a real fullscreen window (`hasFullscreen` and a toplevel whose Wayland `fullscreen` is true; a maximised window keeps the bar and the frame). Each strip is a whole number of physical pixels thick (the first whole length from 1 logical px: 15 at 16/15) with a line of one physical pixel (`1 / Theme.scaleOf(screen)`) on its outer edge. Until then the strips were 2 logical px (2.13 physical) on the Top layer, the line was `Theme.hair + 0.02` because one "pixel" (really 0.53 px, see above) at y=0 was not drawn, and the rail drew the same lines again in case it was on top. Four thin windows rather than one transparent window over the whole screen: less to composite.

## Not covered

- GTK apps (Thunar, libadwaita apps) keep their own rounding: they take colours from the generated `gtk.css`, but their corner radii are in the adw-gtk3 stylesheet and would need a long selector list to override.
- Windows get a 1 px border each and Hyprland has no shared border; with a gap between windows (the grid default) that is no issue, but with a margin of 0 two tiled windows would show a 2 px line.
- Spacing inside the settings window (between sections and rows) and inside popups is layout, not a gap setting, and is unchanged; the cards and rows are square with the stronger edge. Since 2026-10-28 a settings row whose key grid mode replaces shows "Set by grid mode" and the value used, in place of its control (`settings-app.md`).
- Kitty and other terminals: no rounding exists there.
