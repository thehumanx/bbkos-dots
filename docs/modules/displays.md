# Display widget (bar + panel)

Design: `docs/specs/2026-10-18-display-widget-design.md`. Plan: `docs/plans/2026-10-18-display-widget.md`.

Click the monitor/brightness widget in the bar (icon and percentage, left of the volume widget): a popup opens under it. Scroll over the widget changes brightness in 5 % steps. Click outside or press Esc to close.

Files (all under `dotfiles/`; plus `scripts/task16-ddcutil.sh`): `bin/.local/bin/bbkos-display`, `bin/.local/lib/bbkos_theme/{displays,display_cli,brightness}.py`, `quickshell/.config/quickshell/` `services/Displays.qml`, `modules/bar/DisplayWidget.qml`, `modules/panels/DisplayPanel.qml` (+ the `display` entries in `Panels.qml`, `PanelState.qml`, `Bar.qml`), `components/Chips.qml`; `hypr/.config/hypr/hyprland.lua` (loader line and hotplug hooks); tests `tests/theme/test_displays.py`.

## Design

- **One writer.** `bbkos-display` is the only writer of `~/.config/bbkos/displays.json` (the choices) and `~/.local/state/bbkos/theme/hypr-monitors.lua` (generated Lua rules). The shell never writes them: it runs the tool and reads `status` back.
- **Saved per monitor, by description** (`Samsung Display Corp. 0x4187`), not by output name, because names change between docks. Empty or duplicated descriptions fall back to `name:<output>`. A saved layout (mode, main display, position) belongs to the pair of monitors that were connected; any other combination gets Hyprland's defaults (preferred mode, auto scale, auto position).
- **Applied live and at start.** `hyprland.lua` keeps the old catch-all `hl.monitor` rule as fallback and loads `hypr-monitors.lua` after it (`bbkos_load`, a `pcall` that records failures, `theme.md`)`). A change is applied with `hyprctl eval 'dofile("<lua>")'`; a non-zero exit or a new entry in `hyprctl configerrors` puts every file back as it was, evaluates the restored rules again (or the plain fallback rule when there were none) so Hyprland matches the files, and reports the first error line in the panel. `monitor.added` and `monitor.removed` run `bbkos-display apply`, which does nothing (no `hyprctl eval`) when the rendered rules equal the file on disk, so applying the same state twice cannot loop. All three monitor events (and `monitor.layout_changed`) also run `qs ipc call display monitorsChanged`, so Quickshell's copy of monitor and window positions is refreshed (2026-10-25; a move sends no socket event), and since 2026-10-28 the display service's own monitor list too; a status that no longer lists a monitor drops its brightness and error, so a replugged monitor is read afresh (before, an unplugged HDMI kept `20` and `unknown monitor: HDMI-A-1`) (the reviewer found no loop path; a real hotplug was not observed).
- **Keep prompt.** A scale, mode or layout change saves the previous state as `displays-prev.json` (only the first of several changes) and the panel shows "Keep these settings? N s" with Keep and Revert. `Displays.qml` owns the 15 s timer, so closing the panel does not stop the safety revert. `bbkos-display keep` removes the saved state, `revert` restores it and re-applies.
- **Internal panel and the lid.** The internal panel (`eDP*`, `LVDS*`, `DSI*`) is selected by output name, the same selector `bbkos-lid` uses, so the two never hold separate rules for one panel; every other monitor is selected by description. With the lid closed and another monitor enabled, the generated rule for the internal panel is `disabled = true` (never when nothing else would stay on). `bbkos-lid` calls `bbkos-display apply --lid closed|open` after its own raw rule, so the saved scale and layout come back when the lid opens. `BBKOS_LID_STATE=open|closed` or `--lid` override `/proc/acpi/button/lid`.
- **A damaged `displays.json` is never overwritten.** If the file is unreadable, not an object, or has entries `bbkos-display` would drop, `apply` changes nothing (warning only) and `set-scale`/`set-mode`/`layout` refuse with an error naming the file ("fix or remove ..."). The current rules keep running.
- **Unanswered change after a restart.** `displays-prev.json` outlives the shell. When `Displays.qml` finds a pending change at startup (shell restart, crash, logout, reboot) it starts a new 15 s countdown, so the safety revert still happens.
- **Scale options** are 1, 1.1, 1.2 and 1.25 (`SCALES` in `displays.py`; Settings › Displays has a row of chips per monitor over the same list (a slider on the Shell page until 2026-10-28), and the display popup shows its chips). A saved scale outside the list is clamped to the nearest option.
- **Awake mode** (the last row of the popup, `Awake.qml` → `bbkos-awake on|off`). While on, the screen stays on: hypridle's dim (150 s by default; the timers are the `idle.*` settings, `idle.md`), keyboard-light-off (150 s), lock (300 s), screen-off (330 s) and suspend (900 s) listeners all ask `bbkos-awake` (`idle-dim`, `idle-kbd`, `idle-screen-off`, `idle-suspend`), which does nothing while the flag is set. The idle lock (300 s, `idle-lock`) is skipped too, so the screen stays lit and unlocked; the owner's manual lock (keybinding, menu, bar: `loginctl lock-session` / `bbkos-lock`) does not go through `bbkos-awake` and always works. Dim and keyboard-light steps leave a marker so the resume restores only what they changed, and turning awake mode on while dimmed restores the screen at once. Closing the lid still suspends (logind, `bbkos-lid`; what it does is the Lid and power button page, `lid-power.md`). hypridle cannot skip one listener, so the listener asks the script. State is the flag file `~/.local/state/bbkos/awake`; it survives a reboot. Check with `bbkos-awake status`.
- **Layouts (two monitors only).** Extend with the second monitor left/right/above/below the main one (positions computed from logical sizes), Mirror (`mirror = <main output>`), Only this display (`disabled = true` on the other; the main one is never disabled). With three or more monitors every rule gets `position = "auto"` and the saved scale and mode (the layout controls are for two).
- **Brightness is per monitor** (`bbkos-display brightness NAME [PERCENT]`, JSON out). The laptop panel's percent is our own scale (`brightness.py`, `to_percent` / `to_raw`): raw 2 (the floor, so the screen can never go black; raw 0 is off) is **1 %**, the maximum is 100 %, evenly spaced in perceived brightness, percent = 1 + 99 · ((raw/max)^¼ − (2/max)^¼) / (1 − (2/max)^¼). On this panel (400 raw steps) that gives raw 2, 3, 4, 8, 16, 100, 400 = 1, 5, 8, 16, 25, 60, 100 %. The scale is shown the same by the bar, panel, keys and OSD, and it is not `brightnessctl`'s percent (`-m` prints raw 16 as 4 %). It replaced `brightnessctl -e4 -n2` on 2026-10-24, where the same floor read as 27 %. The tool reads the raw value (`brightnessctl -m`) and writes a raw value (`brightnessctl set N`); `bbkos-brightness` (the brightness keys) tells the shell (`qs ipc call display refreshBrightness ""`). Whether raw 1 (one step lower, flicker or tint on the OLED) is usable is untested: the owner has to look at it. An external monitor has no kernel backlight: it is changed over DDC/CI with `ddcutil --bus N getvcp/setvcp 10`, where N comes from sysfs (`/sys/class/drm/cardN-<connector>/ddc -> i2c-N`, no slow `ddcutil detect`). `status` reports per monitor `brightness`: `"backlight"`, `"ddc"` or `null` (no ddcutil or no bus); with `null` the panel shows a hint and the bar widget shows only the icon. The shell runs brightness jobs in their own queue (a DDC call takes up to a few seconds and must not block a scale change) and coalesces a slider drag. DDC jobs are serialised by a lock file (`bbkos-ddc.lock` in `$XDG_RUNTIME_DIR`): overlapping `ddcutil` runs lose the bus lock and print diagnostics with exit code 0. The bar widget on each screen shows and scrolls THAT monitor's brightness. The kernel restores the laptop backlight at boot; DDC values live in the monitor. `scripts/task16-ddcutil.sh` (run with sudo) installs `ddcutil` and makes `/dev/i2c-*` usable for your account.
- **Brightness keys act on the monitor under the pointer.** `bbkos-brightness up|down` runs `bbkos-display brightness @cursor --key up|down` (5 % a press, but 1 % at the dark end: up below 5 %, down at 5 % or below, after Omarchy's brightness keys; `up1|down1` are always `--step ±1`): `@cursor` is the monitor whose logical rectangle (pixels / scale, rotation considered) contains `hyprctl cursorpos`, else the focused monitor, else the first. The laptop panel steps on its percent scale, and a press always moves at least one raw step (at the dark end one raw step is more than 1 %, so a plain +1 % could stay on the same step), an external monitor one DDC read and one write (about 0.4 s a press, measured on the G25F2). The OSD (`qs ipc call osd brightnessOn PERCENT NAME`) appears on that monitor, the widget of that monitor is refreshed, and a monitor without brightness control (no ddcutil, DDC/CI off, no bus) gets a notification instead of silently changing the laptop. The volume OSD now appears on the focused monitor.
- **External monitor speed (2026-10-29).** Measured on the G25F2 over DDC/CI: a read about 90 ms, a write about 115 ms (`ddcutil` 3 tunes its own delays; `--sleep-multiplier 0.5` or `0.2` made it slower, 117-236 ms). A set (the Display popup) no longer reads first: the VCP 10 maximum is remembered per bus and EDID hash in `$XDG_RUNTIME_DIR/bbkos-ddc-max.json` (gone at reboot; another monitor on the same port has another EDID, so it is read again), and `bbkos-display brightness HDMI-A-1 N` went from 263-392 ms to 190-214 ms. In the shell, `Displays.setBrightness` queues at once instead of after a 150 ms debounce: the first press is written immediately, and while one write runs the newest waiting value replaces the others, so a drag is throttled to one write at a time. A key press (`step`) still reads first, it needs the current value. The laptop backlight takes about 80 ms a set.
- **Popups on several screens.** `PanelState` remembers which screen opened a panel (each bar widget passes its own screen name; the power key and IPC use the focused monitor). `Panels.qml` puts one transparent full-screen overlay on EVERY screen while a panel is open, so a click anywhere on any screen closes it; only the target screen shows the card and builds the panel (a second copy would start a second Wi-Fi/Bluetooth scanner). Every overlay asks for **exclusive** keyboard focus, not just the target: with one exclusive layer on screen A and a non-exclusive overlay on screen B, Hyprland sent no pointer events to B at all (measured with temporary logging: no enter, press or click on the second monitor; the first version of the fix looked right in `hyprctl layers` and did not work). Keyboard focus follows the pointer between the overlays. Clicking the same panel's widget on another screen moves the card there.
- **Not in this version:** night light, VRR, HDR/10-bit, rotation, a scale-cycle keybind.

## Commands

`bbkos-display status | set-scale NAME SCALE | set-mode NAME WxH@R | layout extend|mirror|only [--primary NAME] [--position left|right|above|below] | brightness NAME|@cursor [PERCENT | --step DELTA] | keep | revert | apply [--lid open|closed]`. Environment: `BBKOS_DISPLAYS`, `BBKOS_STATE_DIR`. Rescue from any terminal: `bbkos-display revert` (undo the last unconfirmed change) or delete `~/.config/bbkos/displays.json` and `~/.local/state/bbkos/theme/hypr-monitors.lua`, then `hyprctl reload`.

IPC test hooks: `qs ipc call display status | refresh | refreshBrightness NAME | setBrightness NAME N | setScale NAME S | setMode NAME M | setLayout MODE PRIMARY POSITION | keep | revert`; `qs ipc call panel toggleOn PANEL SCREEN` opens a panel on a named screen; `qs ipc call osd brightnessOn PERCENT SCREEN`.

## Verified (2026-10-18)

- 77 unit tests in `test_displays.py` (plus 2 in `test_bbkos_check.py`) for the tool with a fake `hyprctl` (schema, scale options, layout maths, lid handling, brightness backends and `@cursor`, Lua rendering incl. quotes/backslashes/unicode/newlines in descriptions, duplicate descriptions, corrupt file, failed apply restores files, keep/revert, unchanged apply makes no `eval`); whole suite 224 tests.
- Live on this laptop: `bbkos-display status`, `apply` (twice: the second made no change), `hyprctl reload` with the loader line (`configerrors` empty, eDP-1 unchanged at 1920x1200 scale 1.5), `Displays` read through IPC, a no-op change at 1.5 through the real tool: pending, 15 s countdown, `keep` clears it, left alone it reverts by itself after 15 s; panel rendered and screenshotted (brightness slider, monitor card, scale chips, the keep row); `bbkos-check` includes a displays.json check.

## Known limits (final review, 2026-10-18)

- Settings saved for two identical monitors are keyed `name:<output>`; if one is unplugged the other's key becomes its description, so entries saved under the `name:` form stop applying until both are connected again.
- Two commands at the same moment (a hotplug `apply` and a panel click) are not serialised by a lock; the last writer wins.
- A hand-edited `displays.json` holding a number with hundreds of digits makes the tool print a traceback instead of a warning (the rules in force are untouched).
- The Display popup's brightness bar shows the OSD, as volume changes do (changed 2026-10-29 at the owner's request: before, only the brightness keys showed it, which looked broken next to volume). `Displays.setBrightness` emits `brightnessSet(name, percent)` and the OSD shows it on that monitor; re-reads (opening the popup, after a key press) do not emit it, so nothing flashes on open. The widget's wheel on an external monitor goes through the same call; the keys and the wheel on the laptop panel show it through `bbkos-brightness`. `bbkos-check` only checks that `displays.json` is valid JSON.
- Upgrading from the first build of this widget: the old generated file selected the internal panel by description. Run `hyprctl reload` (or log in again) once so Hyprland drops that old rule; until then it may hold two rules for the panel.

## Bugs found by the owner after the first build (2026-10-18)

1. *Brightness of the second monitor changed the laptop panel.* Cause: the only brightness path was `brightnessctl` on `intel_backlight`, the laptop backlight; an HDMI monitor has none and needs DDC/CI (`ddcutil`, not installed). Fix: per-monitor brightness as described above. Verified on the real monitor after `scripts/task16-ddcutil.sh` was run: `ddcutil detect` lists the G25F2 on `/dev/i2c-3` (the bus sysfs gives for `card1-HDMI-A-1`), a read takes 0.17 s, a set 0.27 s, and a key press with the pointer on HDMI changed only HDMI (32 to 37, laptop unchanged). Without ddcutil the monitor shows "Brightness: needs ddcutil and DDC/CI on this monitor". Some monitors ship with DDC/CI switched off in their on-screen menu.
2. *A click on the other monitor did not close a popup (all bar popups).* Cause: `Panels.qml` had one overlay window with no `screen:`, so it existed on one monitor only (`hyprctl layers` showed `bbkos-panel` on eDP-1 and nothing on HDMI-A-1). Fix: one overlay per screen, all with exclusive keyboard focus (above). The first attempt (overlay per screen, exclusive only on the target) was not enough: the layers existed on both monitors but the second one never received the click. Verified by the owner's real click on the second monitor, after logging showed the cause. Not tested: typing into the Wi-Fi password field after opening the Wi-Fi popup on the second monitor (keyboard focus should follow the click into the card).

## Not tested (state plainly)

- Anything with two monitors: mirror, extend, only this display, positions, the main-display chips and the hotplug re-apply were tested only against fake `hyprctl` output. This laptop has one panel.
- A real scale or mode change on the live screen (only a no-op change at the current scale was applied; the changed-value path is the same `hyprctl eval` that the Task 1 probe confirmed with identical values).
- Real mouse clicks on the chips, Keep and Revert, and dragging the brightness slider (only IPC and a screenshot).
- Pressing the physical brightness keys: the script was run by hand with the pointer moved to each monitor (`hyprctl dispatch` cursor move); the Hyprland bind to it was not changed.
- The brightness keys with the new curve reading, and the wheel over the bar widget.
- A first login after a reboot with a saved `displays.json`.
- The lid cycle with the real external monitor (close, open, unplug with the lid closed): the lid logic is covered by unit tests and a `bbkos-lid` dry run only. Which of two same-panel rules wins in Hyprland 0.56.2 was not determined (the by-name selector exists to avoid needing to know).
- The stale-pending countdown after a shell restart (needs an unanswered change; not provoked on your live screens).

## Probe results (2026-10-18, Hyprland 0.56.2)

- **Fields.** `hl.monitor{}` accepts (from `/usr/share/hypr/stubs/hl.meta.lua`, `HL.MonitorSpec`): `output` (required), `mode`, `position`, `scale`, `disabled`, `mirror` (output name), `transform`, `vrr`, `bitdepth`, `cm`, `icc`, `reserved`, HDR/SDR fields. An unknown field is an error: `hl.monitor: unknown field 'bogusfield'`.
- **Live apply works.** `hyprctl eval 'hl.monitor({output="eDP-1", mode="1920x1200@59.999", position="0x0", scale=1.5})'` printed `ok`, rc 0, `configerrors` empty, `hyprctl monitors -j` unchanged (1920x1200 @ 59.999, scale 1.5, 0x0). The `desc:` output form (`output="desc:Samsung Display Corp. 0x4187"`) was accepted the same way. These are the current values, so nothing changed on screen.
- **Errors.** A bad rule exits with rc 7, prints `error: return hl.monitor(...);:1: <message>` and the same line shows in `hyprctl configerrors`. The tool must check the return code and `configerrors` (as `bbkos_theme/reload.py` already does).
- **Mode strings.** `hyprctl monitors all -j` gives `availableModes` as `"1920x1200@60.00Hz"` (and `refreshRate` 59.999). The tool formats modes as `WxH@R` with R rounded to a whole number, and sends the exact `WxH@R` string back.
- **Mirror/disabled/position of a second monitor** cannot be probed here (one panel, `eDP-1`); covered by fake-`hyprctl` tests only.
- **Load order.** Not re-probed with `hyprctl reload` (left alone on purpose); the design relies on a later `hl.monitor` for the same output replacing an earlier one, the same as the generated `hypr-theme.lua` overriding the defaults above it.
