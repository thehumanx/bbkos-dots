# Shell tests

Automatic tests for the shell itself: a static gate that every QML file parses (and qmllint finds nothing new), and a separate test shell (a nested Hyprland with the repo's Quickshell in a temp home) that the tests drive over IPC, without touching the live session, the owner's files or the hardware. Built 2026-10-29 (spec `docs/specs/2026-10-29-shell-tests-design.md`, plan `docs/plans/2026-10-29-shell-tests.md`); closes audit item F6.

## Run

- Everything: `python3 -m unittest discover -s tests/shell -t .` (about 4 minutes: 33 tests, 2 of them opt-in and skipped by default; 9 test shells and one stray nested Hyprland). With `BBKOS_SHELLTEST_VISIBLE=1` the two screenshot tests run too, and their test windows stay on the screen while they run.
- The static gate alone: `python3 -m unittest tests.shell.test_static` (about 10 s). `bbkos-qml-audit` runs the same syntax check, so the usual check before a shell restart catches a file that does not parse ("syntax errors: 0").
- One file: `python3 -m unittest tests.shell.test_popups -v`.
- The live layer skips by itself when there is no Hyprland session, when Hyprland, Quickshell or grim is missing, or when the screen is locked (`pgrep -x hyprlock`, skill rule 14).

## What it covers

| File | What |
|---|---|
| `test_harness.py` | the harness without a compositor: the `with` form starts and always stops; the bar check finds the desktop colour even with something drawn at the centre |
| `test_static.py` | every `*.qml` parses (`qmlformat`, through `bbkos-qml-audit`); `qmllint` counts per file and message id equal `qmllint-baseline.json` |
| `test_start.py` | the test shell starts with no ERROR and no unexpected WARN; the live shell's PID is unchanged; a nested Hyprland left from a crashed run is removed; at start the shell calls only allowed stand-ins |
| `test_popups.py` | all nine bar popups open and close; the Wi-Fi scanner runs only while its popup is open; the owner's `~/.config/bbkos` and `~/.local/state/bbkos` are byte-identical before and after |
| `test_clipboard.py` | the clipboard picker on the test home's own cliphist store: the preview shows a long text in full, a text over 20 KB cut to 20 KB, an image, an image too old to be decoded at open; the chosen row stays chosen when decoding rebuilds the list; the list holds more than 8 rows |

## How the test shell works (`tests/shell/harness.py`)

- **Home:** a temp `HOME` with the built-in defaults (`bbkos-theme defaults`, plus the test's own settings; `remove=["power.chargeMode"]` drops a key), the repo's `matugen.toml`, the theme rendered by `bbkos-theme apply --out-dir` (a dry run: no reload), `~/.local/bin` linked to the repo's commands and the default lock avatar linked from the repo. Nothing of the owner's home is read or written.
- **Compositor:** `Hyprland -c tests/shell/hyprland-test.lua` (scale 1, no animations, blur, shadows or start-hyprland banner, nothing started). Its window opens on the hidden `special:shelltest` workspace of the live session without the focus: before each start the harness adds a runtime window rule on the live Hyprland (`_rule_hidden`: class `^aquamarine$`, `workspace = "special:shelltest silent"`, `no_initial_focus`; the old handle `BBKOS_SHELLTEST` is disabled first). Until 2026-10-31 it opened on the owner's workspace with the focus and was moved away about 65 ms later, so the owner's tiled windows split and snapped back on every test start, a flicker the owner noticed (live event log: `openwindow` on workspace 2, `activewindow` aquamarine, `movewindow` to the special workspace; with the rule only `openwindow` on `special:shelltest`). The move and focus return (`hl.dsp.window.move({ workspace = ..., window = "pid:...", follow = false })`, the focus going back only if the window took it) stay as a fallback, for example after a config reload dropped the rule. **A hidden nested Hyprland does not draw** (it gets no frame callbacks from the live compositor): the shell runs and answers IPC, so the popup, settings and setting tests work, but screen capture hangs, also with a headless output inside it or `render_unfocused` on its window (checked 2026-10-29). So pixel tests are opt-in and keep their window visible (`TestShell(visible=True)`). A nested output takes its window's size (1688x1097 on the laptop), not the mode in the config.
- **Shell:** `quickshell --path dotfiles/quickshell/.config/quickshell` with a clean environment (temp `HOME`, the nested Wayland socket and Hyprland instance, the session D-Bus, `LANG=C.UTF-8`). Ready when `qs ipc --pid` lists `panel`. Driven with `shell.ipc(target, fn, ...)`, `shell.set(key, value)` (the repo's `bbkos-theme set` in the temp home), `shell.screenshot(path)` (grim on the nested output), `shell.log()`, `shell.calls()`.
- **Teardown:** the shell and the nested Hyprland are each started in their own process group and stopped as a group (TERM, then KILL after 5 s), so their children go too; then any process still running with the test home as `HOME`, the temp home and the nested instance's `/run/user/<uid>/hypr/<instance>` directory. Each step runs even if one before it fails. It also runs at interpreter exit (so after Ctrl-C) and on SIGTERM (`timeout ... python3 -m unittest`). A run that was killed outright is cleaned up at the next start: nested Hyprlands started exactly as `Hyprland -c <test config>` and every process whose `HOME` is a `bbkos-shelltest-` temp home are killed (so two runs at the same time would stop each other). `test_start` checks that nothing with the test home survives `stop()`; before this check (found by the final review, 2026-10-29) every test shell left the camera watcher's `inotifywait` behind, 83 of them by the end of the day.
- **The nested instance** is found by its PID in `hyprctl instances -j` (socket and signature), never by guessing from new files.
- **Hyprland 0.56 dispatchers are Lua:** `hyprctl dispatch 'hl.dsp...'`. The old `hyprctl dispatch name args` form only prints a Lua error; the harness's `_dispatch` raises unless the answer is "ok". (Until 2026-10-29 the harness used the old form with the output discarded, so the test windows were never actually hidden.)
- **`hyprctl` reaches the live session unless `HYPRLAND_INSTANCE_SIGNATURE` is the nested one.** Every call meant for the test shell goes through `shell._env()`. (2026-10-29: a probe that set only `WAYLAND_DISPLAY` created a headless output in the live session, which shifted the external monitor until it was removed.)
- **Cost:** a test shell starts in about 1.2 s and uses about 360 MB while it runs (Hyprland 143 MB, Quickshell 214 MB, measured 2026-10-29).

## What is guarded and what is not

- **Stand-ins** (`tests/shell/stub.sh`, first on `PATH`): `sudo systemctl loginctl brightnessctl ddcutil bbkos-brightness nmcli bluetoothctl wpctl rfkill hyprlock bbkos-lock gsettings dconf hyprsunset notify-send uwsm bbkos-camera checkupdates adb v4l2-ctl`, and the power and logind helpers (`BBKOS_POWER_HELPER`, `BBKOS_LOGIND_HELPER`). Each records its call in `$HOME/calls.log` and succeeds. `BBKOS_KITTY_COMM` is set to a name no process has, so `bbkos-theme`'s kitty reload signals no real kitty; `gsettings` stands in so its GTK and cursor reloads do not reach the real dconf. `BBKOS_CLIP_DIR` points the clipboard picker's decoded files into the test home (the runtime directory is shared, and the picker empties its folder on open). `cliphist` is real: with the temp `HOME` it uses the test home's own store.
- **At start** the shell calls only `bbkos-power-apply` and `checkupdates` (both stand-ins; `ALLOWED_AT_START`, checked by `test_start`). The inventory of every `Process` and `execDetached` (2026-10-29) found nothing else that acts on the machine at start.
- **Not guarded, by convention only:** what the shell does over D-Bus directly: Wi-Fi and Bluetooth switches, volume, mute, default device, power profile, notifications. Tests must not trigger those actions; reading (network list, battery) is fine. The live shell keeps the notification server and the polkit agent, so the test shell's registration warnings are expected (`EXPECTED_WARNINGS`).
- Opening the Wi-Fi popup starts a real Wi-Fi scan, and the Bluetooth popup real BlueZ discovery when Bluetooth is on, while they are open (read-only radio use).
- **The camera:** `bbkos-theme`'s reload sets the webcam's controls only when `HOME` is the owner's home (`apply._owner_home`, like the GTK, cursor, idle and night-light reloads), and `v4l2-ctl` is a stand-in too. Before this (found by the final review, 2026-10-29), each `shell.set` in a test reset the real camera to the defaults until the `bbkos-camera` watcher put the owner's values back.
- **The session D-Bus is shared** (a private bus would break `matugen`, which runs through `systemd-run --user`). The live shell owns the notification server and the polkit agent; the test shell only waits to take them over. So do not restart the live shell while the live layer runs: for the rest of the run, notifications would go to the hidden test shell.

## Adding a test

Start a `TestShell` in `setUpClass` (one per file) or per test and always stop it (`addCleanup` or `tearDownClass`), or use `with TestShell(settings=..., remove=...) as shell:`, which stops it even when the block fails; decorate the class with `@skip_unless_session()`, drive it only through IPC hooks and `set`, and end with a check that the log has no ERROR and no unexpected WARN. A new hook for a test belongs in the module's `IpcHandler` with a "test hook" comment, as `settings shown KEY` (2026-10-29). A new expected warning goes into `EXPECTED_WARNINGS` with the reason.

## The qmllint baseline

`qmllint` finds about 3,800 things across the shell, mostly because it cannot see Quickshell's own modules; they are counted per file and message id in `tests/shell/qmllint-baseline.json`, not per line, so moving code does not fail. A count that goes up, or a new file with findings, fails. A count that goes down (tidied code) passes and is printed as a note; fold it into the baseline with `python3 tests/shell/test_static.py --update-baseline` when convenient (look at the diff before committing). Until 2026-10-29 a lower count failed too, which turned the suite red after harmless edits; the owner chose to let it pass.
