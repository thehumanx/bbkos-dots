# Touchpad reset (safety net)

## The problem
The Synaptics touchpad (`SYNA2BA6:00 06CB:CEF5`, I2C HID, two evdev nodes: "Mouse" for the click button and "Touchpad" for touches) sometimes stops sending touches: no cursor movement, scrolling or gestures, while physical clicks still arrive. Seen on 2026-10-20 after the first HDMI monitor connect following a boot (twice), and the same on the owner's earlier Omarchy install. Reloading its driver brings it back.

**Cause: not known.** Ruled out: runtime power management (the device reports `unsupported`), a kernel error (none logged at the time), bbkOS code (the hotplug hook `bbkos-display apply` only rewrites monitor rules; the Hyprland log shows no reload or Lua error). Not shown: the charger. One boot on battery survived the connect, but one boot on the charger also survived it, so charger against battery does not separate the failures. Before the touchpad died the log showed ghost-touch signs ("tool-palm", palm "typing", "kernel bug: Touch jump detected"), which is also what the cursor jumping while typing looks like. Details of the evidence are in the changelog entry of 2026-10-20.

**Update 2026-10-29: the trigger is a monitor hotplug, the charger is not involved.** An HDMI unplug and replug **on battery** (`ADP1/online` 0, "Discharging") broke 2-, 3- and 4-finger gestures again while one-finger movement and clicks kept working. The touchpad's interrupt (`intel-gpio` 160, `SYNA2BA6:00` in `/proc/interrupts`) kept counting while it was used (164765 to 165754), but the Hyprland log had no `[1fg]`..`[4fg]` touch line on the "Touchpad" node after the HDMI connect line, only clicks on the "Mouse" node. So the device still reports, but not as a multi-touch touchpad: it behaves as if it had fallen back to the plain mouse mode a Precision Touchpad starts in, which the driver leaves only when it sets the touchpad input mode at probe; that is why reloading `i2c_hid_acpi` (`bbkos-touchpad-reset`) fixes it every time (it did again; owner confirmed). Why a plug resets the touchpad is not known (an electrical transient or a firmware quirk); not proven without root: the kernel log at the moment of a plug (`sudo dmesg`) and an event trace (`sudo libinput debug-events`) showing the pointer on the Mouse node.

**Open (owner, 2026-10-29: "note it down, revisit later"):** whether bbkOS should run `bbkos-touchpad-reset` by itself a few seconds after a monitor is added or removed (the `monitor.added`/`monitor.removed` hooks in `hyprland.lua` already run `bbkos-display apply`; the cost is a 1-2 s cursor pause after each plug), keep it manual, or first confirm the reset in the kernel log (`sudo dmesg`, `sudo libinput debug-events` around a plug). Nothing is automated yet.

**Update 2026-11-13: mouse mode measured on the device, and the trigger is not only a hotplug.** The fault came back (owner: 2-, 3- and 4-finger gestures dead; "sometimes the charger, sometimes HDMI"). Read with root while it was broken, straight from the two evdev nodes for 10 s (Python reading `struct input_event`; `libinput record` is not installed, the `libinput` tools are not on this machine), the owner moving one finger, then two, three and four: the **Touchpad** node (`event9`) sent **nothing** (0 `ABS_X/Y`, 0 `ABS_MT_POSITION_X/Y`, 0 `ABS_MT_SLOT` ≥ 1, 0 `BTN_TOOL_DOUBLETAP`..`QUINTTAP`), and the **Mouse** node (`event8`) sent **1216 `REL_X/REL_Y`**: the cursor was moving as a plain relative mouse. After `bbkos-touchpad-reset`, the same read: Touchpad node 1179 `ABS_X/Y`, 2375 `ABS_MT_POSITION_X/Y`, 722 `ABS_MT_SLOT` ≥ 1, 11 multi-finger tool flags, 31 key presses; Mouse node 0 of everything. So the device itself leaves Precision Touchpad mode and reports as a mouse, which has no finger count (so no 2-finger scroll and no gestures); libinput, Hyprland and the settings are not involved. Event numbers stayed `event8`/`event9` across this reset. Trigger evidence from the Hyprland log: the HDMI monitor was unplugged at line 95365 and 2-finger scrolls still worked until line 108760 (about 13,000 lines later); between that line and the failure there is no connector line, no input device added or removed, and the kernel log (`sudo dmesg`) has no touchpad, I2C, HID or power-supply line after boot (08:40). The charger was plugged in when read; whether it was plugged or unplugged near the failure is not known (neither log records it). Also seen that day: five `kernel bug: Touch jump detected and discarded` lines on the touchpad before the failure (then libinput's rate limit hid the rest), and the Keychron M7 Bluetooth mouse reconnecting six times, including at the HDMI unplug; neither lined up with the failure. Consequence for the open item above: a reset run on monitor hotplug would not have caught this one. A detector that does not need the trigger: in touchpad mode the Mouse node sends only button events, so any `REL_X/REL_Y` on the SYNA Mouse node means the fault (proposed, not built; needs root to read the node).

How to see it in the Hyprland log (`/run/user/1000/hypr/*/hyprland.log`): count the touchpad's `gesture: [1fg]`/`[2fg]`/`[3fg]` lines after the last `Connector HDMI-A-1 connected` line. Zero after, many before, is this fault. The evdev node number changes between boots, so match the pattern, not `event11`.

## The safety net
- `bbkos-touchpad-reset` (user command, `dotfiles/bin/.local/bin/`): runs the root helper through `sudo -n` and shows a notification with the result. Exit 3 when the helper is not installed.
- `touchpad/bbkos-touchpad-reload` (root helper, installed as `/usr/local/sbin/bbkos-touchpad-reload`): takes no arguments and no environment; removes `i2c_hid_acpi`, loads it again, waits up to 5 s for a touchpad in `/proc/bus/input/devices`, retries the load once. The driver is always loaded again, even if removing it failed. A lock keeps two reloads from overlapping. Exit 0 back, 1 not back (a reboot restores it), 2 arguments given, 3 busy. The touchscreen shares the driver and is reset too.
- `scripts/install-touchpad-helper.sh` (run once with sudo; `--uninstall` removes both): copies the helper and writes `/etc/sudoers.d/bbkos-touchpad`, which lets your account run exactly that file with no arguments and no password (checked with `visudo -cf`).

Use: `bbkos-touchpad-reset` from a terminal, or bind it on Settings › Keyboard › Shortcuts as a custom command. Without a working cursor, type it in a terminal with the keyboard (or a bound key).

## Diagnostic watch (`bbkos-touchpad-watch`, added 2026-11-13)
Owner: "check for this problem on every charger and HDMI connect/disconnect and find if the touchpad has stopped working". A passive logger to find the trigger; it never resets the touchpad.
- `touchpad/bbkos-touchpad-watch` (Python, root, installed as `/usr/local/sbin/bbkos-touchpad-watch`) and `touchpad/bbkos-touchpad-watch.service` (installed as `/etc/systemd/system/`, enabled). Install: `sudo scripts/install-touchpad-watch.sh`; remove: `sudo scripts/install-touchpad-watch.sh --uninstall` (the log is kept). `bbkos-check` compares both installed copies with the repo.
- Logs to `/var/log/bbkos-touchpad-watch.log` (0644, moves to `.1` at 1 MB): `EVENT` for a charger (mains or USB supply) plugged in or unplugged, a DRM connector connected or disconnected, a wake from sleep (CLOCK_BOOTTIME running ahead of MONOTONIC, noticed at the first event after waking), an input device added or removed. Each event is then judged at the **first touch after it**: `OK after:` (the Touchpad node sent touches) or `FAULT after:` (the Mouse node sent REL_X/REL_Y). A fault with no event before it is `FAULT after: nothing`. At a fault it also writes the kernel log lines since the last good touch (`KERNEL`, at most 30). `RECOVERED` when touches come back on the Touchpad node (after `bbkos-touchpad-reset`); events seen while in mouse mode are listed as `NOT JUDGED`.
- Summary (no root): `/usr/local/sbin/bbkos-touchpad-watch --report` prints, per event kind, how often the touchpad was still fine after it and how often it was in mouse mode.
- Sources: `udevadm monitor --udev --property` for `power_supply`, `drm` and `input` (event-driven), the two evdev nodes read without grabbing (Hyprland keeps getting every event), `/sys/class/power_supply`, `/sys/class/drm/*/status`, `dmesg`. No positions are logged, only counts, kinds and times. The nodes are reopened on every input add or remove, since a driver reload kept the numbers `event8`/`event9` while the old descriptors die.
- Cost (estimate, not measured): one Python process, about 10 MB, blocked in `select`, no timer; it wakes for each touchpad report (about 100 a second while a finger moves, which already wake the CPU for Hyprland) and for udev events of those three subsystems (battery `power_supply` changes included, filtered in the script). Meant to run until the trigger is found, then be uninstalled.
- Tests: `tests/touchpad/test_watch.py` (node discovery from this machine's `/proc/bus/input/devices`, mode from raw events, udev parsing, OK/FAULT/RECOVERED judging, the report, the installer under `--prefix`). **Not verified:** the service on the real machine (needs root; my shell here cannot see `/dev/input`, `/sys/class` or the journal), that `udevadm monitor` flushes each event through the pipe, the sleep detection, a real fault being logged.

## Manual reload without the helper
Two separate steps, checking between them: `sudo modprobe -r i2c_hid_acpi`, then `sudo modprobe i2c_hid_acpi`. Chaining them with `&&` once left the driver unloaded and no cursor; unbinding only the touchpad device (`/sys/bus/i2c/drivers/i2c_hid_acpi/unbind`) also left it dead. Last resort: reboot.

## Tests and what was not verified
`tests/touchpad/test_touchpad.py` (installer layout, uninstall, bad user names, the user command with a fake `sudo`, the helper refusing arguments). The root helper itself was not run by the tests or by the agent: it reloads a kernel driver and needs root.
